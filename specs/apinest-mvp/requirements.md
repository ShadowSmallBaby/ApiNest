# ApiNest MVP 需求规格

- **规格名称：** `apinest-mvp`
- **项目名称：** ApiNest
- **状态：** 草案，待确认
- **范围：** 第一阶段（本地优先）
- **目标平台：** Windows、macOS；Linux 作为后续兼容目标

## 1. 背景与愿景

ApiNest 是一款本地优先的跨平台桌面应用，用于统一管理用户本人有权访问的 AI API 中转站账户。它将不同站点的账户状态、余额、用量、模型与签到等用户侧能力收敛到一个界面，同时保证同一站点的多个账号在认证状态、会话资料和操作记录上严格隔离。

第一阶段优先支持顺序为：

1. NewAPI
2. Sub2API
3. CLIProxyAPI（CPA）

产品借鉴 all-api-hub 的“统一资产视图与站点适配”思路，但一期不做浏览器扩展、站点管理员能力、远程同步或凭据跨设备迁移。

## 2. 一期目标

1. 用户可在一个桌面应用中添加、组织和使用多个站点账户。
2. 同一站点 URL 可存在多个相互隔离的账户。
3. 用户可在应用内完成目标站点的登录；一期重点支持 LinuxDo OAuth。
4. 对已认证账户，应用可按站点支持情况查询用户侧信息，并执行签到。
5. 站点差异由适配层封装，界面按能力展示功能，而非散落的平台专属逻辑。
6. 所有数据默认保留在本机，并使用应用级密钥保护敏感资料。

## 3. 非目标

一期明确不包含以下能力：

- 渠道、用户、管理员配置等站点运营管理功能。
- Token/API Key 的创建、编辑、撤销或批量管理；仅允许查看信息或打开站点原生页面。
- GitHub OAuth 作为应用自动化认证流程；可通过站点原生内嵌网页登录使用。
- Passkey 的保存、导出、复制、同步或绕过；仅允许站点原生 WebAuthn 流程调用系统能力。
- 后台常驻定时签到、系统通知。
- WebDAV、云端同步、跨设备凭据同步。
- 站点账户配置的远程同步；未来同步仅考虑非敏感站点信息。
- 绕过验证码、反爬、Cloudflare 或任何站点安全控制。

## 4. 术语

| 术语 | 定义 |
| --- | --- |
| 站点 | 具有固定 `baseUrl`、平台类型与页面路由配置的独立本地实体；一个站点可包含多个账户。 |
| 站点账户 | 某站点上用户的一个独立登录身份，是会话、快照、操作与认证状态的最小隔离单位。 |
| 平台适配器 | 将某类站点的检测、认证、查询、签到和页面路径封装起来的实现。 |
| 内嵌登录 | 在应用控制的独立 WebView 会话中，由用户亲自完成目标站点登录的流程。 |
| LinuxDo OAuth | 目标站点使用 LinuxDo 提供的 OAuth 身份认证能力。 |
| 敏感凭据 | Cookie、Session、API Key、OAuth access token/refresh token 等登录材料。 |

## 5. 用户故事与验收标准

### R1：管理站点账户

**用户故事：** 作为用户，浮浮酱希望添加、编辑、复制和删除自己有权访问的站点账户，以便统一管理不同实例和身份。

#### 验收标准

1. 当用户创建账户时，系统应要求提供平台类型、站点 URL、账户显示名，并允许填写备注。
2. 当用户添加 NewAPI 账户时，系统应允许额外填写可选的 LinuxDo Client ID。
3. 当用户添加不同平台或同一平台的账户时，系统应允许相同 `baseUrl` 被多次使用。
4. 当用户编辑账户时，系统应仅更新目标账户，不应修改同 URL 的其他账户。
5. 当用户复制账户配置时，系统应仅复制非敏感站点元数据，不应复制登录 Cookie、API Key 或 OAuth Token。
6. 当用户删除账户时，系统应先明确提示将删除该账户的本地会话和缓存，并在用户确认后删除；同站点的其他账户不得受影响。

### R2：平台识别与适配优先级

**用户故事：** 作为用户，浮浮酱希望应用协助识别站点类型，同时可以手动纠正识别结果。

#### 验收标准

1. 当用户输入站点 URL 时，系统应尝试检测平台类型。
2. 当自动检测不确定、失败或与用户判断不一致时，系统应允许用户手动选择 NewAPI、Sub2API 或 CPA。
3. 当平台识别完成后，系统应加载对应适配器声明的能力。
4. 系统应按 NewAPI、Sub2API、CPA 的顺序安排一期实现和测试优先级。
5. 当适配器不支持某项能力时，界面不得伪造成功结果，应隐藏该操作或明确显示“不支持”。

### R3：同站点多账号隔离

**用户故事：** 作为用户，浮浮酱希望为同一站点添加多个账号，避免登录状态和查询结果串号。

#### 验收标准

1. 每个站点账户应拥有不可变的本地唯一 ID。
2. 每个站点账户应使用独立的 Cookie Store、WebView Profile 或等效隔离会话容器。
3. 当用户在账户 A 中登录或退出时，账户 B 的会话状态不得改变。
4. 当系统请求余额、用量、签到或模型信息时，应只使用当前站点账户绑定的凭据。
5. 当某账户会话过期时，系统应仅将该账户标记为过期，不得使同站点其他账户失效。

### R4：应用内 LinuxDo OAuth 登录

**用户故事：** 作为用户，浮浮酱希望在应用内完成由目标站点发起的 LinuxDo OAuth 登录，避免手工导出 Cookie。

#### 验收标准

1. 当 NewAPI 账户配置了 LinuxDo Client ID 且适配器确认站点具备对应入口时，系统应发起目标站点的 LinuxDo OAuth 登录流程。
2. 系统应在应用内隔离 WebView 中显示 LinuxDo 或目标站点的官方授权页面，由用户自行输入登录信息、处理验证码或确认授权。
3. 系统不得要求用户在自定义表单中输入 LinuxDo 密码，不得绕过或自动处理验证码、安全验证或授权确认。
4. 当 OAuth 成功回跳并使目标站点建立有效会话时，系统应保存该站点账户所需的会话材料，并验证登录状态。
5. 若用户未填写 Client ID、站点不支持自动流程或自动流程失败，系统应提供“在应用内手动登录”回退入口。
6. 系统可保存 OAuth 流程实际取得且需要维持该账户登录的 LinuxDo 信息，但必须视为敏感凭据并加密；不得保存 Passkey 私钥。

### R5：站点原生手动登录

**用户故事：** 作为用户，浮浮酱希望可在应用内使用站点支持的原生登录方式完成认证。

#### 验收标准

1. 系统应为每个站点账户提供独立的“在应用内登录”和“重新登录”入口。
2. 系统应允许用户在目标站点页面自行使用用户名密码、LinuxDo OAuth、GitHub OAuth、Passkey 或该站点实际提供的其他方式。
3. 当站点原生流程使用 Passkey 时，系统应仅调用操作系统/浏览器的标准 WebAuthn 能力；不得读取、导出、同步或存储 Passkey 私钥。
4. 登录完成后，系统应检测有效的目标站点会话并与当前站点账户绑定。
5. 一期不提供 Cookie 或 API Key 手动导入入口；所有认证均在当前站点账户的应用内会话中由用户完成。

### R6：统一用户侧查询

**用户故事：** 作为用户，浮浮酱希望从统一界面查看各账户的状态和可用信息。

#### 验收标准

1. 对适配器支持的账户，系统应展示登录状态、最后检查时间和错误摘要。
2. 对适配器支持的账户，系统应查询并展示用户资料、余额/额度、用量、可用模型中的任意可用子集。
3. 系统应优先使用站点公开或用户已授权的 API；若没有可用 API，可退化为提供对应网页快捷入口。
4. 系统应保留最近一次成功查询的非敏感缓存，并清晰标识缓存时间。
5. 请求失败、凭据失效或站点能力缺失时，系统应提供可操作的错误信息，不得将失败误报为零余额、零用量或已签到。

### R7：签到

**用户故事：** 作为用户，浮浮酱希望手动为一个或多个支持签到的账户执行签到并查看结果。

#### 验收标准

1. 当账户适配器声明支持签到时，账户详情页应展示单账户签到操作。
2. 总览页应提供“全部可签到账户”批量签到操作。
3. 批量签到应逐账户记录成功、已签到、不支持、会话失效或失败原因。
4. 系统应保存本地签到操作记录，并显示执行时间。
5. 一期不得在未获用户当次主动操作的情况下自动执行后台签到。

### R8：网页与 API 快捷操作

**用户故事：** 作为用户，浮浮酱希望在应用内或外部浏览器中快速打开目标站点的相关页面。

#### 验收标准

1. 对适配器已知路径，系统应提供首页、用户中心、用量页、Token 页和登录页中的可用快捷入口。
2. “应用内打开”必须复用当前站点账户的隔离会话。
3. “外部浏览器打开”只打开 URL，不得假设外部浏览器与应用内会话共享登录状态。
4. 系统应根据适配器能力展示网页入口；不存在的路径不得展示为可用。

### R9：本地优先与数据保护

**用户故事：** 作为用户，浮浮酱希望所有数据仅保存在本机，并通过应用级密钥保护敏感资料。

#### 验收标准

1. 一期不得上传、同步或向第三方服务发送站点配置、账户资料、Cookie、API Key 或 OAuth Token；对目标站点的正常认证和用户主动查询请求除外。
2. 系统应将站点账户元数据、缓存和操作记录保存在本地结构化存储中。
3. 系统应将 Cookie、Session、API Key、OAuth Token 等敏感凭据与普通元数据分离存储。
4. 系统应在首次初始化时引导用户设置应用级主密码或等效应用级解锁密钥。
5. 系统不得保存明文主密码；敏感凭据落盘前必须使用由应用级密钥保护的加密机制。
6. 系统可选择性复用 Windows Credential Manager、macOS Keychain、Linux Secret Service 等系统能力，但其缺失不得阻塞核心本地加密能力。
7. 系统应提供清除指定账户本地会话的操作，并要求用户确认。

### R10：统一总览与本地记录

**用户故事：** 作为用户，浮浮酱希望一眼看到所有账户的健康状态，并定位需要操作的账户。

#### 验收标准

1. 总览应显示账户总数、有效/过期/异常状态和最近操作结果。
2. 对数据语义可确认一致的账户，系统可以展示聚合余额或用量；无法确认币种、单位或口径一致时不得聚合。
3. 总览应突出需要重新登录和最近签到失败的账户。
4. 系统应支持按平台、账户名称和状态筛选账户。
5. 一期的操作历史至少应记录手动刷新、手动签到、登录校验和错误信息。

### R11：应用内嵌页面视图

**用户故事：** 作为用户，浮浮酱希望在主窗口右侧内容区内直接查看目标站点页面，而不是每次都弹出独立子窗口，以便在导航、账户信息和站点页面之间无缝切换。

#### 验收标准

1. 当用户在应用内打开某账户的已知站点页面时，系统应在主窗口的内容区内嵌显示该页面，而非弹出独立操作系统窗口。
2. 内嵌页面视图应绑定该账户专属的隔离会话容器，与其他账户的会话严格分离。
3. 内嵌页面视图应保留在应用外壳的布局约束内，不得遮挡左侧导航或自绘标题栏；切换导航项时应正确显示或隐藏该视图。
4. 内嵌页面视图应沿用受控浏览器容器的全部安全策略：默认拒绝非允许域名导航、`window.open`、下载、权限请求和外部协议，且不向第三方页面注入本应用 Preload。
5. 当用户离开该页面、切换到其他导航项或关闭该视图时，系统应及时释放对应视图资源，且不影响其账户会话的持久化。
6. 当某项操作确需独立窗口（如站点原生弹窗式 OAuth 授权页）时，系统可回退到受控独立容器；此类回退仍受同一套导航与权限策略约束。

### R12：无边框应用外壳与自绘窗口控制

**用户故事：** 作为用户，浮浮酱希望应用拥有统一美观的自绘外壳，而不是系统默认标题栏，以便获得一致的跨平台视觉体验。

#### 验收标准

1. 主窗口应隐藏操作系统默认标题栏与菜单栏，采用应用自绘的顶部区域。
2. 自绘顶部区域应提供可拖拽移动窗口的区域，以及最小化、最大化/还原、关闭控件；控件行为必须与系统窗口状态一致。
3. 应用外壳应采用“锁定页 → 主外壳（左侧导航 + 右侧内容区）”的信息架构；解锁后默认进入主外壳。
4. 左侧导航应列出全部一期规划入口；未实现的入口应显示为占位状态，不得伪造数据或功能。
5. 无边框改造不得削弱既有安全默认值（`contextIsolation`、`sandbox`、`nodeIntegration: false`、`webSecurity`）；窗口控制只能通过受限、类型化的 IPC 通道触发，Renderer 不得获得通用窗口或系统控制能力。
6. 自绘外壳应在 Windows 与 macOS 上均可正常拖拽、缩放与使用窗口控件；平台差异（如 macOS 交通灯位置）应被妥善处理。

### R13：认证方式的类型化管理与会话复用

**用户故事：** 作为用户，浮浮酱希望按认证方式（GitHub、LinuxDo、站点账号密码）分类管理登录入口，让应用为我持久化复用登录状态所需的必要信息，减少重复登录。

#### 验收标准

1. 系统应按认证方式对账户登录入口进行分类，一期涵盖：GitHub OAuth、LinuxDo OAuth、站点账号密码三类。
2. 对 GitHub 与 LinuxDo 两类，一期仅提供“在应用内手动登录”：用户在目标站点或对应身份提供方的官方页面亲自完成认证，应用只在账户专属隔离会话中持久化维持登录所必需的会话信息，实现重启后复用。
3. 应用不得收集、保存或代填 GitHub、LinuxDo 的账号密码；不得绕过或自动处理验证码、二次验证或授权确认。
4. 对站点账号密码类，用户可将其保存为绑定该账户的加密凭据引用（类似密钥引用），仅在用户当次主动发起登录时用于目标站点自身的登录表单；该凭据必须按敏感资料加密存储，绝不写入普通字段、日志、快照或 UI 明文。
5. 站点账号密码的引用只服务于目标站点的原生登录表单填充，不得用于绕过验证码、Cloudflare、Passkey 或任何站点安全挑战；遇到安全挑战时必须交由用户亲自处理。
6. 当某认证方式缺少前置条件（如未配置、站点不支持）时，系统应清晰展示其不可用状态，并提供可用的回退入口，绝不伪造登录成功。
7. 任一认证方式的会话或凭据失效，只能影响其所属账户，不得波及同站点其他账户或其他认证方式。

## 6. 数据与安全原则

1. **最小授权：** 仅保留完成用户明确操作所需的最少凭据和数据。
2. **账户边界：** 任何凭据、缓存和操作均必须绑定唯一站点账户 ID。
3. **本地优先：** 默认不联网同步、不调用产品自有云服务；目标站点通信仅服务于用户主动认证、查询、签到或打开站点。
4. **显式风险确认：** 删除账户、清除会话、导入 Cookie/API Key 等操作必须告知影响并获得用户确认。
5. **不规避安全机制：** 不绕过验证码、反自动化、Cloudflare、Passkey/WebAuthn 或站点访问控制。
6. **可扩展但不预实现：** 数据模型应包含稳定 UUID、时间戳和版本字段，为未来“仅同步非敏感站点信息”保留基础，但一期不实现同步。
7. **账号密码引用受限用途：** R13 的站点账号密码引用仅用于填充目标站点自身的原生登录表单，属于用户主动登录的辅助，与一期非目标中禁止的“Cookie/API Key 手动导入”本质不同——它不导入会话或密钥，不跳过站点登录流程，也不绕过任何安全挑战。

## 7. 成功标准

一期完成后，用户应能在 Windows 或 macOS 上：

1. 添加至少一个 NewAPI 站点的两个独立账号。
2. 对每个账号分别在应用内完成登录，并证明 Cookie/会话不串号。
3. 对支持的 NewAPI 账户查看状态、余额/额度或用量，并成功执行一次手动签到。
4. 使用总览识别一个会话失效账户，而不影响同站点其他账户。
5. 在本地重启应用后，在正确解锁应用数据的前提下恢复账户配置和有效会话。
6. 在不实现 WebDAV 的前提下，确保敏感凭据不会被上传到任何 ApiNest 自有远端服务。

## 8. 后续阶段预留

以下能力不在一期实现范围内，但设计时应避免阻塞：

- Sub2API 与 CPA 的完整适配器实现。
- 定时签到、系统通知。
- 更多站点 OAuth 提供商的专门自动流程。
- 站点信息的端到端加密 WebDAV 同步。
- 跨设备登录与凭据同步（默认仍应关闭）。
- Token 管理、用量可视化和更丰富的用户侧统计。
